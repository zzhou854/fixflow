# FixFlow 高频面试问答

## 1. 这个项目解决了什么问题？

它把住户不精确的自然语言报修转成可信的工单与预约，同时保证权限、状态、并发和失败恢复。核心价值不是聊天，而是让一次长流程最终有明确业务结果或人工接管。

## 2. 为什么不是普通表单？

住户常常只知道“书房开关坏了”，并不知道类别、型号或成因。Agent 可以降低表达门槛、处理多轮修正和相对时间；但正式业务仍由结构化规则执行。对可以用固定字段解决的物业操作，工作台仍使用表格和按钮，不强行聊天化。

## 3. 为什么不用多 Agent？

首版只有三类报修，控制流和责任边界明确。Single Orchestrator 更容易保证 Typed State、身份隔离、Checkpoint 恢复和可审计路由。多 Agent 会引入协调、共享记忆和故障归因成本，当前没有足够业务收益。

## 4. LLM 可以做什么，不能做什么？

可以从当前消息提取有证据的类别、位置、描述、可用时间和风险信号，并在事实白名单内组织回复。不能设置业务状态、授权房屋、生成业务 ID、决定预约成功、修改数据库或直接调用工具。

## 5. 如何防止模型幻觉影响业务？

输入是限长、清洗、白名单上下文；输出使用 `extra=forbid` 的 Pydantic Schema；证据必须来自当前消息；确定性 normalizer、invariant、权限和状态机再次校验。模型给出的时间只是住户可用窗口，候选和预约还要经过数据库规则。

## 6. 为什么使用 MCP？

MCP 提供独立、类型化的业务能力边界，让 Agent 不依赖 ORM 或 Repository。工具 Handler 只适配协议，真正事务仍在 Application Service/UoW。这样可以分别测试语言编排、协议传输和业务一致性。

## 7. MCP 会不会让模型自由调用工具？

不会。图节点是固定的，路由由确定性代码决定，模型 Schema 中没有工具调用字段。MCP Client 只在允许的节点用类型化请求调用固定能力。

## 8. 为什么 Checkpoint 不是事实源？

工作流暂停期间，物业或维修人员可能已经改变工单。Checkpoint 只记录流程状态；恢复时重新读取 PostgreSQL 的最新实体和版本，避免旧 Agent State 覆盖业务事实。

## 9. 怎么保证一个请求不会重复建单或重复预约？

API 请求级幂等解决网络重试，业务命令幂等解决工具重放。作用域、主体和幂等键组成唯一约束，请求 Fingerprint 不同则返回冲突。成功结果与业务写入在同一事务提交。

## 10. 如何处理并发预约？

应用层使用版本条件更新；数据库层保证同一工单最多一个 BOOKED 预约，并用 PostgreSQL GiST 排斥约束阻止同一维修人员时间重叠。数据库异常通过 SQLSTATE 和命名约束映射成稳定业务错误。

## 11. 为什么需要 Transactional Outbox？

如果先提交业务再发事件，进程崩溃会丢消息；如果先发消息再提交，消费者可能看到不存在的业务。Outbox 与业务事实同事务写入，再由带租约 fencing token 的 Dispatcher 至少一次投递。

## 12. UNKNOWN_COMMIT 是什么？

客户端超时不代表数据库没提交。此时不能盲目重试 Mutation。系统创建对账 Case，用 operation、idempotency、aggregate 和 Outbox 等持久证据判断已提交、未提交或需要人工审查。

## 13. Replay 与业务重试有什么区别？

Replay 使用原 Run 捕获的结构化输入和外部结果 Tape，重新执行同一控制逻辑并比较节点、路由、调用顺序、Fingerprint、Interrupt、Mutation Plan 和最终安全状态。它不访问真实 Provider/MCP/业务库/正式 Checkpoint，也不重发 Mutation。

## 14. RAG 如何避免过期政策或 Prompt Injection？

SQL 先做启用状态、类别、主题和有效期过滤；导入与查询 Embedding Profile 必须一致。政策正文被当作不可信 Evidence，只能进入清洗后的事实投影；冲突和充分性由代码判断，政策文本无工具权限。

## 15. DeepSeek Flash 失败怎么办？

传输型错误有限重试一次，Schema 错误只做一次受控修复。总时延预算或熔断耗尽后进入 `HUMAN_REVIEW` 并创建去重人工任务；高风险、权限问题和证据不足不会盲目换模型重试。产品不再调用 Pro，也不回退 Scripted。

## 16. 为什么默认 Provider 还是 Scripted？

在线候选只完成了开发白名单和产品纵向验证，尚未取得新的锁定 Holdout、Shadow 和生产 Canary 证据。保持默认 Scripted 是诚实的发布边界，不影响本地受控演示在线链路。

## 17. 用户说得不精确怎么办？

房间级位置和可观察现象就足够，例如“书房开关坏了”。型号、零件、成因和维修方案不是住户必填项，由维修人员现场判断。只有类别、可定位位置、问题表现和可用时间等住户能回答且流程确实需要的信息才会追问。

## 18. “明天上午”如何处理？

模型可以识别存在时间表达，但常见日段由集中确定性规则解释：上午 09–12、下午 14–18、晚上 18–21，使用请求携带的 IANA timezone。明确钟点不会被该规则覆盖。之后再按 30 分钟粒度生成完整落在可用窗口内的候选。

## 19. SSE 断开会不会丢失业务结果？

不会影响业务事实。SSE 是有界、非持久的体验通道；消息/Resume HTTP 响应和 Thread State API 才是正式结果。重连后通过 State API 对账，阶段 C 的 Trace/Outbox 也不改变这个边界。

## 20. 你在这个项目中最重要的收获是什么？

Agent 工程不能只优化模型正确率。需要同时设计语言边界、业务不变量、事务、恢复、人工接管和用户体验。最关键的原则是：模型输出是候选证据，不是授权，也不是业务事实。

## 21. 你会怎样继续生产化？

先由外部人员审批新的锁定 Holdout，再做 Shadow 和小流量 Canary；同时导入经过物业、合同和地区规则审批的真实政策，补 TLS、监控告警、异地备份恢复演练、值班责任和回退方案。上线决策不能由一次开发集通过自动触发。

## 22. 项目最大的不足是什么？

尚无真实住户流量和生产 SLA；政策语料仍是合成演示数据；住户取消及维修验收暂由人工处理；在线模型未正式激活；开发工具链还有仅影响构建环境的上游安全告警。这些限制在文档中明确记录，没有用功能数量掩盖。

## 23. 为什么不继续无限增加测试？

测试应该对应具体风险。当前规则是：文档检查事实与链接，局部修改跑相关单元/类型检查，事务或 Migration 跑数据库集成，跨层发布才全量验收。真实浏览器发现的时间语义问题说明，产品验收不能被测试数量替代。

## 24. 如果面试官要求你简化系统，你会删什么？

对小型内部试点，可以先保留核心链路：JWT、Single Orchestrator、Application/UoW、PostgreSQL、人工队列和最小 Trace；Replay 与复杂评测控制面可作为后续模块。但不能删除权限、幂等、事务、版本冲突和人工失败出口，因为它们直接决定业务可信度。
