# 简历描述与自我介绍

## 简历项目标题

**FixFlow｜可恢复、可审计的住宅维修协调 Agent**

Python 3.12 / FastAPI / LangGraph / MCP / PostgreSQL / pgvector / SQLAlchemy / React / TypeScript

## 简历三条版

- 从零设计并实现住宅维修协调 Agent，覆盖漏水、电气、门锁三类真实流程；采用 Single LangGraph Orchestrator 与 Typed State，将 DeepSeek Flash 限制在证据化事实提取和受约束回复，权限、状态机、排班与写库全部由确定性代码执行。
- 构建独立 typed MCP 服务与事务型 Application/UoW 层，实现 30 分钟候选时间、技能/服务区域硬约束、请求幂等、乐观锁、GiST 预约防重叠、状态历史和 PostgreSQL 并发一致性。
- 建立失败恢复和审计闭环：Flash 耗尽后转人工，支持工单前人工任务、Transactional Outbox、持久 Trace、UNKNOWN_COMMIT 对账及零业务副作用 Replay；完成真实浏览器三类模糊报修、预约和物业接管验收。

## 30 秒自我介绍

> 您好，我主要关注 Agent 应用如何从 Demo 变成可靠的软件系统。我最近做的 FixFlow 是一个住宅维修协调 Agent，住户可以用生活化语言描述漏水、电气或门锁问题，模型只提取有证据的结构化事实，权限、状态转换、预约和数据库写入仍由确定性代码控制。我围绕它实现了 LangGraph、MCP、Policy RAG、事务并发、Outbox、Trace、对账和 Replay，也用真实浏览器修复过无回复、错误时段和人工闭环等产品问题。这个项目让我形成了一个明确的方法：把概率能力放在语言层，把可验证性和业务责任留在工程层。

## 90 秒自我介绍

> 您好，我的方向是 Agent 应用开发和智能系统工程。我不希望项目只是调用一次大模型 API，所以在 FixFlow 中选择了一个失败代价明确的住宅报修场景。住户往往只会说“书房开关坏了”或“洗手池下面滴水”，系统需要理解自然语言，但不能让模型决定权限、状态和写库。
>
> 我采用 Single LangGraph Orchestrator 管理多轮状态和中断恢复，用 DeepSeek Flash 做严格 Schema 的事实提取，再由确定性代码判断缺失信息、安全风险、服务时长和路由。业务操作通过独立 MCP 服务进入 Application Service、Repository 和 Unit of Work，PostgreSQL 负责工单事实，使用幂等、乐观锁、部分唯一索引和 GiST 排斥约束处理并发预约。
>
> 为了验证失败路径，我还实现了 Outbox、持久 Trace、UNKNOWN_COMMIT 对账和隔离 Replay。最近的真实浏览器验收中，我定位并修复了模型失败时用户没有正确回复、“明天上午”被解释成凌晨、物业确认弹窗失效等问题，并完成了 Flash 失败后人工认领和办结的闭环。我希望应聘的岗位也是这种既需要模型能力，又重视业务边界、可靠性和产品体验的 Agent 工程方向。

## 与因果发现项目结合的两分钟版本

> 我的项目经历有两条互补主线：一条是 FixFlow 这样的 Agent 应用工程，另一条是正在推进的因果发现数据项目。
>
> 在因果发现中，我关注的是数据进入算法前是否可信，例如变量定义、时间对齐、缺失值和异常值处理、离散与连续变量编码、滞后关系、共线性、选择偏差，以及如何把领域先验转成允许边、禁止边或时间顺序约束。因果发现不是把表格直接扔给算法，而是先判断数据生成过程、可识别性假设和稳定性，再比较结构学习结果。
>
> FixFlow 则把同样的思路落到在线系统：模型输出不是事实本身，只是带证据的候选解释；系统还要经过授权、状态机、政策证据、数据库版本和人工边界验证。我认为二者的共同点是区分“观察到的数据”“模型给出的判断”和“系统允许采取的行动”。前者训练了我对数据质量和因果假设的敏感度，后者训练了我把不确定模型嵌入可靠业务流程的工程能力。

因果项目尚未提供可核实指标时，不要临场虚构数据量、算法精度或论文结论。可以按真实进展补入：数据规模、变量数量、采用算法、稳定性方法和当前结果。
